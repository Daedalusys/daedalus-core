## 1. 三台宿主怎么来的

靶机 `Masterwet_Server` 上没有现成的 Debian 12 / CentOS Stream 9 宿主,但 **KVM 可用**
(`/dev/kvm` 可写),于是就地起三台 cloud image 虚机:

| VM | 镜像 | distro |
| --- | --- | --- |
| `vmu` | `noble-server-cloudimg-amd64.img` | Ubuntu 24.04.5 LTS |
| `vmd` | `debian-12-genericcloud-amd64.qcow2` | Debian GNU/Linux 12 (bookworm) |
| `vmc` | `CentOS-Stream-GenericCloud-9-latest.x86_64.qcow2` | CentOS Stream 9 |

每台:**12G qcow2 overlay + NoCloud seed(cloud-init)+ 用户态网络端口转发**
(`hostfwd tcp:127.0.0.1:<宿主端口>-:22` 与 `-:9443`)。用用户态网络而不是网桥,是为了
不动宿主网络配置,且宿主 `127.0.0.1:<agent端口>` 直接映射到 guest 的 9443 —— 控制面
就跑在宿主上,拨 `localhost` 正好命中 server 证书的 SAN。

宿主机上的准备步骤(可复现,全部真实执行过):

1. `sudo dnf install -y cloud-utils genisoimage`(提供 `cloud-localds` 造 seed ISO);
2. 造**共享 PKI**:一张 CA + 每台一份 server 证书(`SAN=DNS:localhost`)+ 一张控制面
   客户端证书(见 §7.1 为什么必须共享);
3. 每台预置 `/etc/daedalus-agent/config.yaml`(含各自的 `agent_id`)与
   `/etc/daedalus-agent/tls/{agent.pem,agent.key,ca.pem}` —— **必须在 `install.sh` 之前**,
   否则 agent 首启会自举自己的 CA 并把预置材料覆盖掉;
4. 刷新宿主包索引(`apt-get update` / `dnf makecache`,见 §6.4);
5. **按回滚点造不对称**:`vmu` / `vmd` 装 `rsync`(→ `SNAPSHOT_CAPABILITY_RSYNC_TARGET`),
   `vmc` 不装 `rsync`、也没有 btrfs(→ `SNAPSHOT_CAPABILITY_NONE`,充当 vendored 夹具里
   那台 `legacy-no-snapshot`)。

## 6. 真机上撞出来的四个问题

前两个是**驱动自身的缺陷**(已在本分支修掉并有 selftest 钉子),后两个是环境/宿主就绪问题。

### 6.1 远端命令的嵌套引号把矩阵静默打断

`remote_agent_id` 原写 `... | tr -d ' \""`,本地双引号字符串里 `\"` 只消掉一层,远端实际
收到的是 `tr -d ' "` —— **一个未闭合的单引号**。ssh 以 2 退出,又撞上 `set -e`,整个矩阵
在装完第一台之后**没有任何输出**地中断。

- 现象:日志停在 `ok - ubuntu: install.sh 退出 0`,后面全没了。
- 处置:远端命令整体单引号包住、内部只用双引号(改用 `sed -n "s/^agent_id:[[:space:]]*//p"`);
  另加 `trap ... ERR` 指名意外失败的行号,不再允许"静默中断"。
- selftest 无法覆盖这类问题(需要真远端),靠真机跑暴露。

### 6.2 dpkg 的字段语法写成了 rpm 的

`pkg_probe_cmd` 的 dpkg 分支原写 `-f="%{Status}\n%{Version}\n"` —— `%{...}` 是 **rpm** 语法,
dpkg-query 用的是 `${...}`。这个错误**在包没装时看不出来**(输出是 "no packages found"),
只有包真装上之后才原样吐出 `%{Status}`,于是判定把**真装好的机器误报成没装**。

- 现象:`install ok installed` 明明在机器上,驱动却报"目标机上并未确证 nginx 已装"。
- 处置:改用 `-f='${Status} ${Version}'`;并补一条 selftest 用例
  (`dpkg 字段占位符没被展开(写成 rpm 的 %{Status})→ 判没装上`)把这个坑钉住。

### 6.3 包管理器提示语是本地化的

靶机 `LANG=zh_CN.UTF-8` 时 `rpm -q nginx` 输出 `未安装软件包 nginx`,不是
`package nginx is not installed`。判定对两种文本都 fail-closed(都不会误判为已装),
但已统一加 `LC_ALL=C` 把输出钉成英文。已固化成 selftest 用例。

### 6.4 cloud image 的包索引可能是过期的

Ubuntu 24.04 cloud image 预置的 apt 索引指向 `nginx 1.24.0-2ubuntu7.18`,而归档里该版本
已被撤下:

```console
$ ssh vmu 'sudo apt-get install -y nginx'
Err:1 http://security.ubuntu.com/ubuntu noble-updates/main amd64 nginx-common all 1.24.0-2ubuntu7.18
  404  Not Found [IP: 91.189.92.22 80]
E: Unable to fetch some archives, maybe run apt-get update or try with --fix-missing?
```

此时 agent 回报 `exec: persistent failure: apt: unclassified failure: Reading package lists...
(exit status 100)`。这是**与 agent 无关**的宿主就绪问题(索引过期),已在准备步骤里加
`apt-get update` / `dnf makecache`。

- 附带观察(不构成缺陷,仅记录):该错误文案只截取了输出的首行 `Reading package lists...`,
  真正可操作的 `E: Failed to fetch ... 404` 被丢掉了。执行器对未分类失败一律按
  `ErrPersistent` 处理符合其既有契约(不可重试),但**首行截断**让排障变难。

## 7. 两处设计发现

### 7.1 agent 自举 CA 与"一个 Plan 一份客户端证书"是冲突的

`daedalus-agent` 首次启动会在 `ca_path`/`ca_key_path` 处**自举一张自己的 CA**;而控制面对
一个 Plan 里的所有节点只持有一份客户端证书(`fleet.DialConfigFromEnv` 的三个环境变量是
全局的)。三台各一套 CA 时,`plan submit` 连任何一台都握不上手。

- 结论:**必须在 agent 首启之前把同一张 CA 预置进每台**,并由它签发各自的 server 证书
  (SAN = 控制面拨号地址的 host 段)。本轮的准备步骤就是这么做的,已写进驱动头部说明。
- 影响面:这是"多节点一次性 Plan"的部署前提;单节点手工 `node add` 场景不暴露。

### 7.2 RF3 对所有 ApplyIntent 生效,所以"无回滚点节点"进不了低危腿

`ApplyIntent` 在 `SNAPSHOT_CAPABILITY_NONE` 上一律拒(不限风险等级),因此一台没有回滚点的
机器**连低危 intent 也接不了**。驱动的低危腿因此只打有回滚点的节点,把无回滚点的节点留给
高危腿验"下发前就被拒";这不是迁就测试,而是被验对象的真实语义。

## 8. 与期望不符之处

- **第三台的 `support_level` 是 `experimental`,不是 `supported`**。spec §7.1 的支持矩阵列的是
  `rhel 9/10`,不含 `centos`;CentOS Stream 9 的 `ID=centos`,按
  `internal/fleet/support.go` 的判定落 `experimental`。这不是缺陷 —— 分级诚实度就是
  "矩阵外一律 experimental" —— 但它与"三台 RHEL 系都该 supported"的直觉不符。**按实记录,
  未改判定表去迁就**。若要覆盖 CentOS Stream,应另开 issue 谈是否扩矩阵。
- **低危腿只覆盖了 2 台(vmu/vmd)**。第三台 vmc 被设计成 `legacy-no-snapshot`(无 rsync/btrfs),
  按 §7.2 它连低危 intent 也接不了,故归高危腿。"三宿主各一份记录"仍然成立:三台都有
  `node list` 行、都参与了 Plan 判定,只是参与的是不同的腿。

## 9. 未覆盖项

- **人审恢复路径(`plan advance --skip/--force`、本地 `daedalus-tx rollback`)未演练**:
  本轮高危腿是"下发前就拒绝",没有任何机器被动过,`recovery` 为空,没有可恢复的对象。
