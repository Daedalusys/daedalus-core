## 1. 为什么真机三宿主现在跑不了

本 Task 的低危腿要跑的是"agent 真把 nginx 装上,且目标机独立核实到"。它依赖
`daedalus-agent` 的真执行器(Task 1–6)。当前 `daedalus-agent` `main` 上 `apply` 仍是
`applyStub`:只打一行日志就 `return nil`,而控制面因此拿到 `SUCCESS`。前置 PR
`feat/agent-real-executor` **尚未合并**(截至本文件写作时,该仓 `loficore/agent-real-executor`
分支与 `main` 同点,无新增提交)。

在这个状态下真跑,低危腿的结论必然是"控制面报 complete 而目标机上没有 nginx" —— 那重现
的是已知的 `applyStub` 问题,不是本 Task 的判据,也不该记成本 Task 的失败。故真机部分按
计划约定写 BLOCKED,并列出所需宿主规格(§5.1)与合并后要跑的命令(§5.2)。

### 3.1 这些用例各自钉住了什么

- **控制面判定腿**:直接复用 core 既有的 `tests/integration` 端到端判据(真双向 TLS +
  真 `Scheduler` + 真夹具 + 本地 fake agent),覆盖"低危 Plan 全部落地且每条结果都带
  `tx_id`"和"高危 Plan 遇无回滚点节点在下发**之前**就被拒、整批 dirty"两个判定。
  这里**不重复实现**控制面那一半 —— plan-c 的驱动与夹具是同一份。
- **独立核实腿**:`pkg_installed_from_output` 是低危腿的判据来源。它只认包管理器给出的
  确证形状(dpkg 的 `install ok installed`;rpm 的首行 `<pkg>-<数字>…`),空输出、
  探测报错、形状不认识一律判"没装上"(fail-closed)。
- **负对照**:这是本 Task 最要紧的一条 —— 构造一个"控制面报 `complete` + 带 `tx_id`,
  但目标机上并没有这个包"的场面,断言判定**必须不通过**。`applyStub` 的教训就是
  "自我汇报的 SUCCESS 不可信",这条负对照把它钉成可重复的判据。
- **Plan 生成物**:真机上的 `machine_id` 必须等于注册表里的 `node_id`,而 agent 侧
  `Register` 返回的 `node_id` 是 `<agent_id>-<随机后缀>`(见 `daedalus-agent/internal/rpc/register.go`),
  静态夹具的 `machine_id` 在真机上对不上 —— 故 Plan 由脚本按 `node list` 实测值现场生成。
  该生成物被喂给**真的** `objectmodel.Plan.Validate()`(经 `daedalus-host plan submit`),
  在"节点未注册"处才停,说明结构合法;反证用例把 `blast_radius.count` 改坏,校验器确实拒。

## 4. 目标机独立核实:真机上的原样命令与输出

低危腿的判据命令由 `pkg_probe_cmd` 生成,下面是它在**真机**上跑出来的原文。

### 4.1 Ubuntu 24.04(`ssh Ali_ECS`)

```console
$ ssh Ali_ECS 'LC_ALL=C dpkg-query -W -f="${Status}\n${Version}\n" nginx 2>&1 || true'
dpkg-query: no packages found matching nginx
```

`nginx` 当前未装 —— 这是低危腿执行**之前**的基线。真跑后这里应该变成
`install ok installed` + 版本号,否则判定不通过。

### 4.2 rpm 家族(`ssh Masterwet_Server`,Fedora 44)

```console
$ ssh Masterwet_Server "rpm -q nginx 2>&1 || true"
未安装软件包 nginx

$ ssh Masterwet_Server "rpm -q bash 2>&1 || true"
bash-5.3.9-3.fc44.x86_64
```

上面两条是 `LC_ALL=C` 之前跑出来的(见 §4.3)。加了 `LC_ALL=C` 之后:

```console
$ ssh Masterwet_Server "LC_ALL=C rpm -q nginx 2>&1 || true"
package nginx is not installed

$ ssh Masterwet_Server "LC_ALL=C rpm -q bash 2>&1 || true"
bash-5.3.9-3.fc44.x86_64
```

### 4.3 一条真实发现:包管理器的提示语是本地化的

- **现象**:靶机 `LANG=zh_CN.UTF-8` 时,`rpm -q nginx` 输出 `未安装软件包 nginx`,而不是
  `package nginx is not installed`。
- **期望**:探测输出与判定不随宿主 locale 变化。
- **实际**:判定本身对两种文本都是 fail-closed(两种都过不了"首行必须是 `<pkg>-<数字>`"
  的形状检查,都会判"没装上"),**判定不会因本地化而误判为已装**;但输出文本会随 locale 变脸。
- **处置**:探测命令统一加 `LC_ALL=C` 前缀,把输出钉成英文。理由不是"怕误判",而是去掉
  整整一类"换个 locale 就变脸"的不确定性,并让证据文件里的输出可跨宿主直接比对。
  该发现已固化成 selftest 里的一个用例(`rpm 报本地化提示(zh_CN 的"未安装软件包")→ 仍判没装上`)。
- **影响 / issue**:无独立 issue —— 这是本 Task 新增驱动自身的实现选择,已在同一提交里修好,
  没有遗留到别的产物里。

## 5. 三宿主真跑(BLOCKED)

### 5.1 所需宿主规格

| 宿主 | 现状 | 规格(每台) |
| --- | --- | --- |
| Ubuntu 24.04(`ssh Ali_ECS`) | **已就位** | 已有:2 vCPU / 1.6 GB RAM / systemd 255 / 免密 sudo |
| Debian 12 | **BLOCKED: no host** | ≥2 GB RAM、systemd、root 或免密 sudo、x86-64(能跑 Go 静态二进制)、可从本机 ssh 到 |
| CentOS Stream 9(或 RHEL 9) | **BLOCKED: no host** | 同上;若用 CentOS Stream 9 注意其 `ID=centos` 会落在 support 矩阵外 → `experimental`(见 §9) |

共同前提(与宿主无关):

1. `daedalus-agent` 的 `feat/agent-real-executor` 已合并,并能产出出货 tarball
   (`daedalus-agent-<version>/{bin/daedalus-agent, scripts/install.sh}`)。
2. 控制面 mTLS 客户端凭证三件套:`DAEDALUS_FLEET_CLIENT_CERT` / `DAEDALUS_FLEET_CLIENT_KEY` /
   `DAEDALUS_FLEET_CA`。
3. 目标机与 agent 的 TLS 互认:agent 首启会 bootstrap CA 与自己的服务端密钥对
   (写 `/etc/daedalus-agent/tls/`),控制面客户端证书需由该 CA 签发(或经既有 PKI 对齐)。

### 5.2 合并后要跑的命令

```bash
export DAEDALUS_AGENT_TARBALL=/path/to/daedalus-agent-<version>.tar.gz
export DAEDALUS_FLEET_CLIENT_CERT=/path/to/client.pem
export DAEDALUS_FLEET_CLIENT_KEY=/path/to/client.key
export DAEDALUS_FLEET_CA=/path/to/ca.pem

# 可拨地址缺省时脚本会用 `ssh <别名> hostname -I` 的第一个值;NAT/公网地址场景显式给 @addr
tests/fleet/agent-e2e.sh --hosts \
    ubuntu=Ali_ECS@<控制面可达的IP> \
    debian12=<ssh别名>@<addr> \
    rhel9=<ssh别名>@<addr>
```

脚本会自动:逐台读 `/etc/os-release` → 装 agent → `node add`(带 `--distro` /
`--distro-version` / `--hostname`)→ `node list` 断言 → 低危 Plan + **目标机独立核实** →
高危 Plan 只打无回滚点节点、断言当场 dirty 且 `tx_id` 全空、`recovery` 为空。

### 5.3 matrix 分支冒烟(注入 ssh 替身;真 agent 缺失,预期红)

真机跑不了,但 matrix 分支的每一行都需要至少执行过一次 —— 否则交付的是一段谁也没跑过的
shell。做法:用脚本自己的注入缝 `DAEDALUS_SSH` 指向一个罐装 ssh 替身(按远端命令返回
固定输出),再喂 dummy 凭证与 dummy tarball。

```bash
DAEDALUS_SSH=<替身> DAEDALUS_AGENT_TARBALL=<dummy.tar.gz> \
DAEDALUS_FLEET_CLIENT_CERT=<dummy> DAEDALUS_FLEET_CLIENT_KEY=<dummy> DAEDALUS_FLEET_CA=<dummy> \
  tests/fleet/agent-e2e.sh --hosts ubuntu=smokehost
```

输出原文(节选;退出码 `1`):

```text
== 被控机基础信息(目标机自己的 /etc/os-release;不采信 agent 自报)
  ok   - ubuntu(smokehost): ID=ubuntu VERSION_ID=24.04 PRETTY_NAME="Ubuntu 24.04.5 LTS"
    uname -r: 7.0.0-38-generic

== 逐台安装 daedalus-agent(出货 install.sh)
  ok   - ubuntu: install.sh 退出 0

== 登记被控机(daedalus-host node add)
node add: fleet: 加载客户端证书失败: tls: failed to find any PEM data in certificate input
  FAIL - ubuntu: node add 127.0.0.1:9443 失败

== node list 契约
  FAIL - 节点数 = 1(jq: .nodes | length == 1)
    实际输出: {"nodes":[]}
  ok   - 每行 support_level ∈ {supported, experimental}

== 低危腿:package.set nginx(low)→ 目标机独立核实
  ok   - 低危 Plan status=complete
  FAIL - 低危 Plan 每条目标机都有落地记录(jq: .results | length == 1)
    实际输出: {"plan_id":"agent-e2e-low","status":"complete","max_risk":"low","batches":[],"results":[],"recovery":[]}
  ok   - 每条落地记录都有非空 tx_id(本地有回滚点)
  [独立核实] ubuntu: $ LC_ALL=C dpkg-query -W -f="%{Status}\n%{Version}\n" nginx 2>&1 || true
    install ok installed
    1.24.0-2ubuntu7
  ok   - ubuntu: 目标机上确证 nginx 已装(独立于控制面/agent 的自我汇报)

== 高危腿:只打没有回滚点的节点 → 期望当场 dirty(且什么都没下发)
  FAIL - 没有 snapshot 能力为 NONE 的节点,高危腿无法按预期执行(不下发高危变更);记为偏差

agent-e2e: 6 通过 / 4 失败
```

红的那三条都是**替身导致的预期红**:替身后面没有真 agent,`node add` 的 mTLS 握手必然失败,
于是 `node list` 为空、高危腿也就挑不出无回滚点的节点。真 agent 就位后这三条应当是绿的。

**冒烟的价值在于它抓到了一个真空过**:第一版只断言低危 Plan `status == "complete"`,
而**零目标机的 Plan 同样会报 `complete`** —— 也就是说,即便一台机都没登记成功,低危腿也会
"通过"。上面那条 `低危 Plan 每条目标机都有落地记录` 断言就是为此补的,补完后同一冒烟立即
变红(`.results | length == 1` 不成立)。这条发现来自真实执行,不是推演。

## 8. 待前置 PR 合并后核实的两处跨仓契约缝(未复现,故未开 issue)

这两条是读代码得出的**待核实项**,不是已复现的缺陷,因此按纪律只登记、没开 issue。
合并后真跑时若命中,应各自开 issue。

1. **`kind` 的线上取值 vs 执行器注册键**。控制面下发时发的是
   `Kind: string(t.Intent.Kind)`(`daedalus-core/internal/fleet/scheduler.go`),而对
   `package` / `service` 这类资源,`objectmodel.Kind` 的字面量是 `package` / `service`;
   计划的 Task 2 写的注册键是 `"package.set"`(以及 `"file.set"` / `"service.set"`)。若
   agent 侧直接以计划里的字面量注册、不做映射,则 `exec.Apply` 查表会落空并 fail-closed
   返回 `ErrUnsupportedKind`,低危腿会以 `persistent` 失败收场。
2. **低危夹具的 `spec` 形状**。`tests/fleet/fixtures/plan-low-nginx.json` 的
   `spec` 是 `{"version": "1.24.0"}`,而 Task 2 的执行器读的是 `desired_state`
   (`present|absent|latest`)。本脚本因此不使用那份静态夹具,改为现场生成
   `spec: {"desired_state": "present"}` 的 Plan;静态夹具是否仍适用于真 agent,
   需要合并后一并确认。

## 9. 与期望不符之处

- **CentOS Stream 9 的 `support_level` 预期**:spec §7.1 的支持矩阵列的是 `rhel 9/10`,
  不含 `centos`。若第三台用 CentOS Stream 9,其 `ID=centos` 按
  `internal/fleet/support.go` 的判定会落 `experimental`。这**不是缺陷**(分级诚实度:
  矩阵外一律 experimental),但与本 Task 文案里"RHEL 三宿主"的直觉不符,真跑时按实记录,
  **不得**为了让它显示 `supported` 去改判定表。
- **`--hosts` 的可拨地址**:agent 监听 `:9443`(mTLS),控制面必须能主动拨到它。`Ali_ECS`
  这类经 NAT 的宿主,`hostname -I` 给的是内网地址,故脚本支持 `key=别名@可拨地址` 显式覆盖;
  真跑前需确认控制面到该地址的可达性。
