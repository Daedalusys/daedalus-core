## 4. 这一轮证明了什么

issue #156 要求的五件事,逐条对上:

| #156 的要求 | 判据 | 结果 |
| --- | --- | --- |
| 200 台能跑完 | 200 条结果、每条带 `tx_id`、`status=complete`、每台恰好 1 次 `ApplyIntent` | ✅ |
| 提交延迟 / JSON 尺寸可量化 | 5.5 s / 47,637 字节 | ✅ |
| 批序:importance 下 supported 先 | 批 0 = 100 台 supported,批 1 = 100 台 experimental,且两批都被下发过 | ✅ |
| 高危 → 首败即脏,后续批零下发 | 无回滚点那台 `ApplyIntent` **0 次**;后续批调用计数 **0** | ✅ |
| 低危瞬时失败只重试失败机 | 失败机 3 次、其余各 1 次,最终 complete | ✅ |

**两个"停手"的口径被分开了**(这正是这一轮最该被钉住的地方):

- **高危那台**:一个 RPC 都没发出去(`ApplyIntent` 计数 0)——控制面在准入阶段就拒;
- **不可达那台**:RPC 发出去了但连不上(计数不为 0),第 2 批整批脏,**第 3、4 批的
  计数是 0** —— 停手发生在批次边界。

## 5. 量到但**没有改**的两件事(如实记)

1. **注册表是 O(n²) 的文件 I/O**:`Registry.Put` / `MarkSeen` 每次都**整表读 + 整表写 + fsync**
   (`internal/fleet/registry.go` 的 `Put` / `MarkSeen` / `store`)。200 节点 × 1 intent
   ≈ 400 次整表重写,这是 5.5 s 里的主要成分。**本轮只量不改**(计划里写明:产品改动要另开
   issue、另一次评审)。规模再上一个量级时这里是第一个要动的地方。
2. **连不上的节点走的是"立即拒绝"而不是"等超时"**:TCP 连接被拒是立刻返回的
   `codes.Unavailable`,所以死节点用例只花 2.0 s,**没有**等满 60 s 的 `defaultCallTimeout`。
   这条链没被覆盖到的是"连得上但 RPC 挂住"的场景(那才会烧 60 s)。

## 6. 未覆盖(如实记)

1. **没有 200 台真机器**。本轮是假 agent(#156 明确说假 agent 够);真机矩阵目前是 4 台
   (见 `2026-11-16-agent-e2e.md` / `2026-11-16-plan-c-e2e.md` / `2026-11-16-landing-check.md`)。
2. **没有控制面 HA**。单控制面进程,200 台。
3. **调度器是串行的**(生产代码零并发),200 台 = 200 次串行 mTLS 握手。本轮**没有**测并发,
   也没有改调度器去加并发 —— 加并发会改变"半成功整批停手"的时序语义,那是另一件事。
4. **只有 1 条 intent、1 种 kind**(`package.set` 低危 + 一条高危)。`file` / `service` /
   `container` 三类 kind 在 200 台规模下未测。
5. **批次大小只测了 50**;`size=1`(200 批)与 `size=200`(1 批)未测。
6. **`plan advance` 的人审恢复路径未测**(那是 `cmdPlanSubmit` 之外的另一条命令)。
