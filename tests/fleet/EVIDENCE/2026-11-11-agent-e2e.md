### 6.1 执行前基线

第一次矩阵跑之前(三台都没装 nginx;这一段是 `dpkg-query` 找不到包时的输出):

## 7. 遇到的问题

### 7.1 驱动的低危腿选点前提过期(矩阵的唯一失败,15/1)

**现象**:三台节点的 `snapshot_capability` 全是 `SNAPSHOT_CAPABILITY_NONE`,驱动的

```bash
if [ -z "${caps[i]}" ] || [ "${caps[i]}" = "SNAPSHOT_CAPABILITY_NONE" ]; then
    echo "  ${keys[i]}: 无回滚点,低危腿跳过(RF3 会拒;归高危腿)"
    continue
fi
```

把三台全筛掉,于是低危腿**一条都没跑**,矩阵以 `FAIL - 没有任何有回滚点的节点,低危腿无法执行` 收尾。

**根因**:agent 侧已经改成"回滚点按 kind 判、与宿主快照机制无关":

- `daedalus-agent@e7906e5 feat(rollback): copy 后端兜底,宿主快照机制停用`
- `daedalus-agent@a0ca20f feat(rollback): 按 kind 判定回滚点`
- `daedalus-core@a634896 fix(fleet): 高危闸门按 intent 判回滚点,file 不再被误拦`

agent 的 `internal/snapshot/capability.go` 现在**恒报 NONE**(宿主的 btrfs/rsync 探测函数保留但生产路径不再调用),
目标机日志里能直接看到这行:

```text
$ ssh vmu "sudo journalctl -u daedalus-agent --no-pager | grep -i 'snapshot capability' | tail -1"
Nov 11 02:54:35 vmu daedalus-agent[5656]: 2026/11/11 02:54:35 agent: snapshot capability reported as NONE by design (host snapshot mechanisms are not probed); rollback points are per-kind and use the built-in copy backend
```

而 `package` 这个 kind **本来就没有回滚点**(`internal/rollback/point.go`:`PointFor("package")` → `PointNone`,
回滚点只给 `file` 的单文件 copy)。于是当前语义是:

- **低危** intent:控制面照发(`runOne` 只拦"高危且无回滚点"),agent 照做(`apply_intent.go` 只在
  `point == PointNone && risk == HIGH` 时拒)—— §5 的补验证明低危 package 确实落地了。
- **高危** intent:控制面在下发**之前**就拒(`refused_snapshot_capability_none`)—— §6.3 证明什么都没下发。

**处置**:本轮**没有改 `agent-e2e.sh`**(任务边界明确),失败如实记录;低危腿用同一条控制面路径
(`node add` → `plan submit`)单独补验(§5 + §6.2),独立核实到三台真的装上了 nginx。
驱动自身的选点前提需要按新语义更新(应按 **intent kind** 而不是宿主 `snapshot_capability` 选点),
这是一条**驱动缺陷**,不是产品缺陷。

### 7.2 agent 装好后自报的 snapshot capability 与驱动注释不符

`agent-e2e.sh` 头注释与 §7.2 的旧结论都写着"agent 的 RF3 对**所有** ApplyIntent 生效(不限风险等级),
没有回滚点的节点连低危 intent 也会被拒"。该结论在当前代码下**已经不成立**(见 §7.1),驱动注释与
实际语义脱节。本轮未改注释(边界要求),记录在此。

### 7.3 `dpkg-query` 的状态串有两副面孔(不是缺陷,记录)

同一台机器上,nginx 从未装过是 `dpkg-query: no packages found matching nginx`;装过又被 `remove` 之后是
`unknown ok not-installed`。两者都**不含** `install ok installed`,所以驱动的 fail-closed 判定
("证不出来就是没装上")在两种情形下都成立,只是输出形状不同 —— 写证据时不能把二者混为一谈。

### 7.4 本轮未复现的旧问题

2026-11-06 那轮撞到的三件事在本轮**没有复现**:(1) 远端嵌套引号把矩阵静默打断 —— 驱动已是
`remote_agent_id` 单引号包裹的写法;(2) dpkg 字段语法写成 rpm 的 `%{Status}` —— 驱动已用 `${Status}`;
(3) cloud image 的 apt 索引过期 —— `provision-kvm-hosts.sh` 已在准备阶段 `apt-get update` / `dnf makecache`,
本轮三台装 nginx 均一次成功。

## 10. 重跑:修正驱动后的矩阵

> 本节是**新增**的一轮,不改上面 §0–§9 的任何历史记录。首轮那个失败(§7.1)是驱动缺陷的
> 真实证据,保留原样。

### 10.1 驱动改了什么(只改 `tests/fleet/agent-e2e.sh`)

1. **低危腿不再按 `snapshot_capability` 筛点**:`node list` 里的节点**全部**进低危腿。
   旧注释("RF3 对所有 ApplyIntent 生效,没有回滚点的节点连低危 intent 也会被拒")已按新语义
   改写:RF3 只拦"高危且无回滚点"的 intent,低危 intent 不因节点缺回滚点被拒;回滚点按
   intent kind 判是 agent 内部的事,不是低危腿的选点条件。
2. **高危腿的选点与理由改为按 kind**:新增判定原语
   `node_has_rollback_point <node-kind> <intent-kind> <snapshot-capability>`,与控制面
   `internal/fleet` 的 `intentHasRollbackPoint` 同语义(`file` + agent 有内建单文件 copy 点;
   其余 kind 只能靠宿主快照机制,能力为空 / NONE / UNSPECIFIED 视为没有)。高危腿打
   "`package` 在这个节点上没有回滚点"的节点 —— agent 节点上 `package` 改宿主状态、没有
   内建回滚点,只能靠宿主快照机制,故**所有 agent 节点**都归高危腿。`render_high_plan`
   的注释、高危腿的 `step` 标题与 `bad` 文案、拒绝文案的断言描述一并改准。
3. `tx_id` 断言描述改成中性说法:**`tx_id` 是事务 id,不等于"有回滚点"**。
4. **控制面拒绝文案逐字未动**(仍是 `节点 … 无回滚点(snapshot capability=…):high-risk
   intent 拒绝下发——无回滚点 ≠ 可继续`),控制面源码本轮一行未改。
5. `--selftest` 新增 4 条回滚点判定断言(14 → 18);旧断言一条没删、没为了变绿改行为。
