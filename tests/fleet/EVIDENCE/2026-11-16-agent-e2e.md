## 2. 结论:core#141 要的那两件事,真机上成立

### 2.1 高危腿当场 dirty 且**一个 RPC 都没发**

判据是**目标机 agent 审计链的行数零增长**(不是 `tx_id` —— 控制面在拒绝路径同样不给 `tx_id`,
所以空 `tx_id` 证明不了"没下发"):

```
== 高危腿:container(既无内建回滚点也无执行器凭据)→ 期望当场 dirty 且一个 RPC 都不发
  ok   - 高危腿:plan 当场 dirty
  ok   - 高危腿:文案点名无回滚点(container)
  ok   - 高危腿:ubuntu 的 agent 审计链 27 → 27 行(零增长 ⇒ 一个 RPC 都没发)
  plan submit(container,high): {"plan_id":"agent-e2e-high","status":"dirty","max_risk":"high","batches":[{"index":0,"node_ids":["e2e-u24-b69b0c47"]}],"results":[{"node_id":"e2e-u24-b69b0c47","intent_id":"agent-e2e-high/e2e-u24-b69b0c47/0","node_kind":"agent","intent_kind":"container","outcome":"persistent","result":"refused_snapshot_capability_none","tx_id":"","message":"节点 e2e-u24-b69b0c47 无回滚点(agent 节点:container 类变更既无内建回滚点、执行器也不产回滚凭据;自报 snapshot capability=\"SNAPSHOT_CAPABILITY_RSYNC_TARGET\"):high-risk intent 拒绝下发——无回滚点 ≠ 可继续"}],"recovery":[]}
```

逐项对照 issue 里写的"要做":

| issue 的要求 | 本轮真机结果 |
| --- | --- |
| 高危夹具不再用 `package` + `kernel-core`(会在真机上真装内核包) | 夹具 kind = `container`;`kernel-core` 在驱动里 **0** 次 |
| 文案断言与本仓事实源一致 | 实际文案「无回滚点(agent 节点:container 类变更既无内建回滚点、执行器也不产回滚凭据…)」,与 `internal/fleet/scheduler.go` 一致 |
| "零 RPC"要有硬判据 | 目标机审计链 **27 → 27** 行;读不到行数时 fail-closed 记 `bad` 且不下发 |
| 目标机不被碰 | `recovery:[]`;高危腿未触发任何执行器凭据 |

> **注**:被控机自报 `snapshot capability="SNAPSHOT_CAPABILITY_RSYNC_TARGET"`(有 rsync 目标),
> 但 `container` 类变更**既无内建回滚点、执行器也不产回滚凭据** → 仍被拒。这正是
> "落点/凭据口径 ≠ 宿主快照能力口径"那条设计主张的真机体现。
