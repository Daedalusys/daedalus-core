## 7. 与期望不符之处

**照实写**。每条格式:`现象 → 期望 → 实际 → 影响 → issue 号`。

### D0(前置缺陷,本次已修):夹具机器名 ≠ 真 `node_id`,高危夹具顺序不对

- **现象**:控制面按 `node_id` 找节点(`internal/fleet/scheduler.go:213` → `Registry.Get`,
  比的是 `NodeID`),而 `node_id` 由 agent 在 Register 时自报
  (`<agent_id>-<8hex>`,`daedalus-agent/internal/rpc/register.go:93`),夹具里的
  `ubuntu24-a` 之类是静态模板名。
- **期望**:`plan-c-e2e.sh --hosts …` 能直接跑通。
- **实际**:首次运行前即发现,故本次先把驱动改成运行期渲染(`render_plan`:
  用 `node add` 回读的 `node_id` 替换夹具机器名,映射不全则拒提交),并把无回滚点那台
  排到第一批(与集成测试 `tests/integration/fleet_e2e_test.go:158` 的手工 swap 同一意图)。
- **影响**:不修则第一条断言就 `节点 ubuntu24-a 未注册`;不改顺序则高危腿会先真去
  Ubuntu 上装 `kernel-core`,dirty 原因变成装包失败 —— 验收结论假阳性。
- **issue 号**:已随 `cd08add` 修复(驱动侧),无独立 issue。

### D1(设计层不一致,需 owner 拍板):高危准入对 agent 节点不看节点的快照能力

- **现象**:高危 `package` intent 在 `e2e-u24-f2295738`(`snapshot_capability=RSYNC_TARGET`)
  上同样被拒,文案写 `snapshot capability=SNAPSHOT_CAPABILITY_NONE/"SNAPSHOT_CAPABILITY_RSYNC_TARGET"`。
- **期望**:`objectmodel.HasRollbackPoint` 的注释说"package / service 的回滚点取决于
  节点自带的快照机制 —— 那是节点维度的事",但 `internal/fleet/scheduler.go:58`
  的 `intentHasRollbackPoint` 对 agent 节点**只**看 kind(`HasRollbackPoint` 恒等于
  `kind == file`),节点能力不参与准入。
- **实际**:`package` 高危在**任何** agent 节点上恒被拒;模板"含一台无回滚点(其余有)"
  的前提不成立,§5 第 3 个勾无法为是。
- **影响**:验收单证明的是"高危 package 在 agent 上必停",而不是"有回滚点的机器能落地、
  没有的才停"。后者需要先拍板准入口径(准入看能力 / 文档改口径 / 夹具换 kind)。
- **issue 号**:`daedalus-core#130`(P1 / P0.5 fleet / Blocked=需设计决策)。

### D2(诊断误导,可修):拒绝文案把常量 `NONE` 当成节点能力值打印

- **现象**:同一句式 `snapshot capability=SNAPSHOT_CAPABILITY_NONE/<实际值>`,
  前一段是硬编码常量,后一段才是节点真实能力。读的人会以为节点能力就是 NONE。
- **期望**:文案里的能力值与节点自报值一致。
- **实际**:`internal/fleet/scheduler.go:283` 的 `fmt.Sprintf` 用 `snapshotCapNone`
  填了第一段,节点真实值在第二段(`%q`)。
- **影响**:诊断误导(会让运维以为 `RSYNC_TARGET` 的机器没有回滚点);
  不影响判定结果。
- **issue 号**:`daedalus-core#131`(P2 / P0.5 fleet)。

### D3(靶场可用性,可修):开发态策略文件回溯只认目录名 `daedalus-core`

- **现象**:`daedalus-host plan submit` 在宿主副本(`~/daedalus-e2e/core`)上
  fail-closed:`policy: 未找到 policy.toml(生产路径与仓库回溯均未命中)`。
- **期望**:开发态从仓副本跑控制面应能命中策略文件。
- **实际**:`daedalus-sdk/policy/policy.go:47` 的回溯候选写死
  `daedalus-core/files/system/opt/daedalus/shared/policy.toml`(跨仓平级 clone 时命中),
  副本目录名不叫 `daedalus-core` 就命中不了;`DAEDALUS_POLICY_MODE=development`
  是开发回退开关,本次**刻意不用**(要验的是生产策略,不是内置默认)。
- **影响**:靶场必须显式设 `DAEDALUS_POLICY_PATH`,否则控制面直接拒跑。
- **issue 号**:`daedalus-sdk#54`(P2 / Stage=未定 / Area=sdk)。

### 附:已核实不算缺陷的两点

- **`node_id` 的进程态**:两次独立运行拿到的 `node_id` 完全相同
  (`e2e-u24-f2295738` 等),说明 agent 进程未重启时后缀稳定;agent 一重启后缀会变,
  登记表里的旧行随即失效(`Registry.Get` 报"未注册")。本轮登记与提交在同一会话内完成,
  未踩到。**风险登记,不是本轮缺陷**。
- **台数与命名**:`node list` 恰 4 台;`vmc` 只登记一次(同名 guest 二次登记会因
  `node_id` 去重而互相覆盖,故 `rhel9-a` 用了 `vmr` 而不是 `vmc`)。
