## 6. 与期望不符之处 / 未验证项

### 6.1 官方 Red Hat 仓库未验(装包源临时指向 AlmaLinux 9)

vmr **未注册订阅**(`subscription-manager identity` → `This system is not yet registered`),
`cdn.redhat.com` 无 entitlement(`curl -k` → 403),`dnf` 直接连官方仓库会得到空仓库集合。

因此 `provision-kvm-hosts.sh` 的 `rhel)` 分支先写一个**仅用于测试**的
`/etc/yum.repos.d/daedalus-test-alma.repo`(`daedalus-alma9-baseos` / `-appstream`,
BaseOS + AppStream,`gpgcheck=1` + Alma 公钥),再用
`dnf -y --disablerepo='*' --enablerepo='daedalus-alma9-*'` 装 `rsync`。
矩阵低危腿的 `unzip` 也来自这个源(`unzip-6.0-60.el9.x86_64`,与 Alma 上同版本)。

**结论**:「systemd / sudo / 包索引可刷新 / 装包落地」都在真 RHEL 9.9 上验过,
但**「Red Hat 官方仓库可用」这条未验**。要补这一条,需要在 vmr 上
`sudo subscription-manager register --username <账号> --auto-attach` 后重跑一次装包腿。

### 6.2 只有 RHEL 9.9,没有 RHEL 10

矩阵写的是 `rhel 9/10`,本轮只覆盖 9(`9.9`)。RHEL 10 需要另一份 cloud image(同为开发者订阅下载),
未取、未跑。core#112 的标题是「RHEL 9/10 行无宿主可验」,本轮把其中 **9** 补齐,10 仍缺。

### 6.3 vmr 的 snapshot 能力是 RSYNC,不是 LVM_SNAP

见 §3.2:RHEL KVM Guest Image 的根是裸 xfs 分区,vma(Alma)是 LVM。两者同族但能力不同。
对矩阵准入**没有影响**:`392d779` 之后 agent 节点的高危闸门只按 kind 判,
宿主快照能力不参与准入;`SNAPSHOT_CAPABILITY_RSYNC_TARGET` 也不等于「package 有回滚点」(§4.6)。

### 6.4 高危腿证明的是「拒绝」,不是「回滚」

高危腿只证明:无回滚点的 `package` intent 在准入阶段被拒、`tx_id` 为空、没有机器被动过。
RHEL 上的**实际回滚/恢复**未验(卷级回滚已转出为 `daedalus-core#120`)。

### 6.5 既有字段缺口(非本轮引入)

`node list` 里 `kernel` / `arch` / `agent_version` / `cert_fingerprint` 仍为空字符串。
分级不依赖这些字段,本轮未改。

### 6.6 未跑 file 腿

本轮驱动只按 `--package unzip` 跑 package 腿(与 core#112 验收一致);
file 腿在 `2026-11-11-agent-file-e2e.md` 里单独验过,未在 RHEL 上重跑。

## 8. 结论

RHEL 9.9 KVM guest(`vmr`)接入五台靶场后,与前三台异构宿主 + AlmaLinux 9 跑同一条脚本、同一张 CA:
`install.sh` → mTLS 注册(`distro=rhel 9.9` → `supported`)→ 低危 `package.set unzip` 五台全落地
(目标机 `rpm -q` 独立核实)→ 高危 `package.set kernel-core` 第一批被拒(`dirty`,`tx_id` 全空)。

矩阵里 `rhel 9` 这一行从此有真宿主证据;`rhel 10` 与「RHEL 官方仓库可用」仍为缺口,已单列于 §6。
